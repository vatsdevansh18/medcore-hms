# CLAUDE.md

Guidance for Claude Code sessions working on MedCore HMS.

## What this project is

A multi-tenant Hospital Management Platform, built under a strict phase-gated methodology. **Read `docs/05-DEVELOPMENT-PLAN.md` first** to find the current phase, then the specific `docs/*.md` files relevant to the work at hand. `docs/phase-reviews/PHASE-X-REVIEW.md` files record what's actually been completed and gated — treat them as more current than this file for "where are we."

**`docs/12-QUALITY-PROTOCOL.md` is mandatory reading before doing any implementation work in this repo.** It's a user-mandated, standing rule (not a suggestion) covering the implement→verify→root-cause-fix→re-verify cycle, mandatory negative/edge-case testing, continuous security review, multi-tenancy/RBAC verification requirements, "no fake completion," and the full phase-review format. A phase cannot reach PASS without going through it.

## Non-negotiable rules

- **Never start a phase's implementation without the user's explicit "START PHASE N."** Finishing a phase means writing `docs/phase-reviews/PHASE-X-REVIEW.md` (format: `docs/12-QUALITY-PROTOCOL.md` §23) and stopping — not silently continuing to the next phase.
- **The brief (`docs/source/InternMo_HMS_Brief.docx`) is the source of truth for scope.** `docs/01-PRD.md` refines it; `docs/11-DECISIONS.md` records every place scope, architecture, or the brief's own suggestions were interpreted, extended, or deviated from, with rationale. Check that file before assuming a gap is an oversight — it's probably a documented decision.
- **Tenancy isolation and RBAC are release-blocking, not "nice to have."** Any change touching a tenant-scoped model must go through the three-layer enforcement in `docs/03-ARCHITECTURE.md` §5. A cross-tenant data leak is a Critical defect that blocks the phase gate outright.
- **All requirement/security/test IDs are stable.** `FR-*`, `NFR-*`, `SEC-*` IDs defined in `docs/02-SRS.md` and `docs/09-SECURITY.md` are never renumbered — a superseded one is marked `[SUPERSEDED by ...]`, never deleted or silently reused.
- **`packages/types` is the single source of truth for API shapes.** DTOs/enums are added there first, then consumed by both apps — never duplicated ad hoc in one app.
- **Never declare a real TypeScript `enum` in `packages/types`.** Use the `as const` object + derived union-type pattern already used throughout `packages/types/src/enums.ts`. Two `enum` declarations with identical members are not mutually assignable in TS, and Prisma generates its own enum types from `schema.prisma` independent of this package — a real enum here makes every Prisma query result fail to type-check against service/DTO signatures (found in Phase 3; full reasoning in the enums.ts file header and `docs/phase-reviews/PHASE-3-REVIEW.md`).
- **A schema-changing edit to `apps/backend/prisma/schema.prisma` always needs a new migration in the same change**, not a follow-up. Reset + reseed (`prisma migrate reset --force --skip-seed && pnpm run db:seed`) is the normal way to apply it locally — there's no real data to preserve pre-launch.

## Monorepo conventions

- Package manager is **pnpm** (workspaces); do not introduce npm/yarn lockfiles.
- `@medcore/types` is consumed as compiled JS (`dist/`), not raw TS — it has a real `build` step because neither `ts-node` (backend dev) nor Next's compiler transpile arbitrary TypeScript found inside `node_modules` by default. **Any edit to `packages/types/src/*` requires `pnpm --filter=@medcore/types run build` (or a root `pnpm run build`) before the change is visible to either app** — its `dist/` is stale otherwise, and the failure mode is a confusing runtime error (e.g. `Cannot read properties of undefined (reading 'SOME_ENUM_MEMBER')`) rather than a type error, since `ts-node --transpile-only` skips type-checking.
- `packages/config` holds the shared ESLint flat-config base and TS base `tsconfig`; app-specific configs extend it rather than redefining rules. The frontend is the one exception — it uses Next's own `eslint-config-next` directly (documented in `docs/phase-reviews/PHASE-1-REVIEW.md`) since it already bundles the React/Next-specific rules our generic base doesn't cover.
- Node/pnpm versions: `package.json` `engines` states minimums (`node >=20`, `pnpm >=9`), not exact pins — the local dev machine may run newer versions. Docker images and CI pin exact versions (`node:20-alpine`, pnpm `9.15.4`) for reproducibility. Don't "fix" the `engines` field to match local `node --version`.
- Docker Compose (dev) bind-mounts each app's `src/` for hot reload but **bakes `packages/` in at image build time** — after editing `packages/types`, run `docker compose build api frontend` before `docker compose up` picks up the change.
- **`TenantContext.run()`/`.bypass()` always await the callback internally** — never change this to a bare pass-through. `AsyncLocalStorage` context reliably survives native `await` chains but not Prisma's lazy `PrismaPromise` thenable when the caller's own callback isn't `async`; wrapping the callback in an internal `async () => callback()` inside `TenantContext` itself (rather than trusting every call site to write `async () => { await ... }`) is what makes this safe regardless of caller style. Full story in `tenant-context.ts`'s doc comment and `docs/phase-reviews/PHASE-3-REVIEW.md`.
- **A cross-cutting concern that needs `AsyncLocalStorage` (or anything else) active for the _entire_ request pipeline must be a NestJS Interceptor, not a Guard.** A Guard's `canActivate()` only controls the synchronous window before the controller runs; by the time the controller executes, whatever a Guard set up has already unwound. `TenantContextInterceptor` is the reference example — the architecture doc calls this "TenantScopeGuard," but it's implemented as an interceptor for exactly this reason.
- **Watch for circular imports between a DI token's owning module and any provider that `@Inject`s that token from outside the module.** If `redis.module.ts` imports `SomeService` to register it, and `SomeService` imports the token back from `redis.module.ts`, the token can be `undefined` at evaluation time. Fix: put the token itself in a tiny standalone file (e.g. `redis.constants.ts`) that both sides import from, never re-exported through the module file.
- **Every e2e spec that boots a real Nest HTTP app (`createNestApplication()` + `app.init()`) must call `configureApp(app)` from `src/common/bootstrap/configure-app.ts`, never assemble its own subset of `main.ts`'s config.** `main.ts` and every such spec previously drifted independently, and no e2e spec ever registered the global `ValidationPipe` — meaning `whitelist`/`forbidNonWhitelisted`/`transform` were silently never exercised by any e2e test from Phase 3 through Phase 4, and query-string numbers (`page`/`limit`) arrived at services as raw strings instead of the numbers `@Type(() => Number)` is supposed to produce. Found in Phase 4; full story in `docs/phase-reviews/PHASE-4-REVIEW.md` Bugs Found #4.
- **Never bind a `PaginationQueryDto` and a second `@Query("field")` separately on the same handler.** Under the global `ValidationPipe({ forbidNonWhitelisted: true })`, NestJS validates the *whole* incoming query object against the *first* bound DTO class — any field the first DTO doesn't declare is rejected outright, even though a second `@Query()` binding for it exists on the same method. Add the extra field(s) to a DTO that `extends PaginationQueryDto` instead (see `FindDoctorsQueryDto`/`FindPatientsQueryDto`) and bind it through a single `@Query()`. Found in Phase 4; `docs/phase-reviews/PHASE-4-REVIEW.md` Bugs Found #3.
- **Any Prisma query that returns a `User` row or a relation to one (`include: { user: ... }`) in an API response must use `SAFE_USER_SELECT`** from `src/common/prisma/safe-user-select.ts`, never a bare `include: { user: true }` or an unselected `prisma.user.create/findUnique`. A bare include returns every column, including `passwordHash` — this leaked a real bcrypt hash into `POST /doctors`/`POST /patients`/`POST /users` responses in Phase 4 (`docs/phase-reviews/PHASE-4-REVIEW.md` Bugs Found #2) before being fixed at all 7 call sites.
- **Catching a Postgres `EXCLUDE USING gist` constraint violation (e.g. the appointment double-booking guard) must also catch deadlock (`40P01`), not just the exclusion violation itself (`23P01`).** Two truly concurrent inserts into the same GiST-indexed exclusion constraint can make Postgres detect a deadlock between the two transactions' index-page locks and abort the loser with `40P01`, with no `23P01` anywhere in that transaction's own error — confirmed via a direct-to-Postgres repro (25/25 truly-concurrent insert pairs raised `40P01`, never `23P01`). Both codes mean the same thing from the caller's perspective ("you lost this race, the DB is the source of truth") and should both translate to the same clean conflict response. Found in Phase 5; full story in `docs/phase-reviews/PHASE-5-REVIEW.md` Bugs Found #2.
- **A pure-ESM npm package (`"type": "module"`, e.g. `@nestjs/bullmq`/`bullmq`, or `puppeteer`/`puppeteer-core`) fails to load under `ts-jest`'s e2e config with a parse error** unless it's carved out of the default `transformIgnorePatterns` (which excludes all of `node_modules` from transformation by default). Fix is a `transformIgnorePatterns` override in the Jest config allowing `ts-jest` to transform that specific package, not a code-level workaround. See `apps/backend/test/jest-e2e.json`. Found in Phase 5 (bullmq), recurred in Phase 7 (puppeteer) — check this file first whenever a new npm package throws `SyntaxError: Unexpected token 'export'` under Jest.
- **`puppeteer`'s bundled Chromium download does not run on `node:20-alpine` (musl libc)** — same class of gap as the Prisma engine binary. Install Alpine's own `chromium` package via `apk add` and point Puppeteer at it with `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium-browser` + `PUPPETEER_SKIP_DOWNLOAD=true` set *before* `pnpm install` runs in the Dockerfile, so the image never wastes a download it can't use. Native dev is unaffected (those `ENV` vars are Dockerfile-only). See `docs/11-DECISIONS.md` D-016, `infrastructure/docker/Dockerfile.backend`. Found in Phase 7.
- **`prisma migrate dev` refuses to run at all in a non-interactive shell** (Claude Code's Bash tool included) the moment it needs to show any confirmation prompt — e.g. adding a `@unique` constraint, even to an empty table — failing with "Prisma Migrate has detected that the environment is non-interactive." `--create-only` does **not** avoid this; the prompt-detection happens before that flag matters. When this happens: hand-write the migration's `migration.sql` (match the exact naming Prisma already uses elsewhere in `prisma/migrations/*/migration.sql` — `<Table>_<column>_key`/`<Table>_<column>_fkey`, `ON DELETE SET NULL` for an optional relation vs. `RESTRICT` for a required one), then apply it non-interactively with `prisma migrate deploy` (this command never prompts), then `prisma generate`. Found in Phase 7.
- **`@aws-sdk/client-s3`'s default `requestChecksumCalculation` ("WHEN_SUPPORTED") signs an `x-amz-checksum-crc32` requirement into every presigned `PutObjectCommand` URL it issues, but a presigned URL's body is uploaded later by a client the SDK never sees — nothing ever computes/sends that checksum, so every presigned upload is rejected** (confirmed against LocalStack: `"Value for x-amz-checksum-crc32 header is invalid"`; real AWS S3 has the same requirement, so this isn't LocalStack-specific). Fix: construct the `S3Client` with `requestChecksumCalculation: "WHEN_REQUIRED"` — see `src/common/storage/s3.service.ts`. Found in Phase 6.
- **A local S3-compatible endpoint (LocalStack, `docker-compose.yml`'s `localstack` service) is required for both native dev and e2e tests that touch attachments** — `docs/11-DECISIONS.md` D-015. Bring it up with `docker compose up -d localstack` before running EMR e2e specs; `S3Service.onModuleInit` self-provisions the dev bucket against it automatically, but only when `S3_ENDPOINT` is set (never against real AWS).
- **`$queryRaw`/`$executeRaw` bypass the tenant-scoping Prisma extension entirely** (it only hooks model operations). Every raw query touching a tenant-scoped table must bind `"hospitalId" = ${hospitalId}` explicitly, taken from the caller's JWT via TenantContext and never from request input. Always use the tagged-template form (parameterised), never `$queryRawUnsafe` with interpolated strings. See `StockService.lockMedicines` and `MedicinesService.findLowStock`. Found while building Phase 9's row locks.
- **Any write that changes a medicine's available stock or its `reorderLevel` must run inside a `$transaction` that first calls `StockService.lockMedicines` (a `SELECT ... FOR UPDATE` on the `Medicine` rows) and then `StockService.evaluateLowStock`.** The per-medicine lock is what stops concurrent dispenses overselling a batch; it was verified by removing it, which made the concurrent-dispense e2e test fail. `evaluateLowStock` maintains the FR-PHARM-004 once-per-crossing latch (`docs/11-DECISIONS.md` D-022), and skipping it silently loses alerts. Lock order is prescription row first, then medicines sorted by id, to stay deadlock-free. Found in Phase 9.
